# Exploration #6 — Standalone API / MCP

**Research date: 2026-11-11. Decision: defer; re-score API/MCP from the placeholder 2.0/5 to 1.5/5 for the current launch. REST first if customer evidence later justifies it.**

An incrementality API is a real product form: Incremental publishes campaign-level incremental ROI through GraphQL, and WPP Media describes integrating those metrics into its own planning tools; Recast exposes executable measurement/planning APIs and a hosted MCP server. These are stronger precedents than a directory listing, but they do not establish demand for our particular observational audit, its prices, or an API-only purchase. For us, an endpoint adds tenancy, security, billing, retention, support, and the risk of machine-speed causal overclaims while leaving the estimator's known failures intact. Keep the current human review gate, finish real-seller pilots, and obtain repeat paying customers before building a private REST integration for a committed buyer. Add hosted MCP only when that buyer needs an agent workflow. A registry listing can make an existing service easier to connect; inbound demand from it remains unverified. Sources checked 2026-11-11: [Incremental measurement API](https://docs.incremental.com/docs/common-use-cases/measurement/), [WPP Media integration announcement](https://www.wppmedia.com/news/incremental-first-agency-connected-partner), [Recast APIs](https://getrecast.com/introducing-recast-apis/), [Recast MCP](https://docs.getrecast.com/docs/mcp-setup-guide).

## 2. Form — REST API vs MCP server vs both

**Top finding: build a durable asynchronous audit service first; MCP is an adapter to the same jobs, authorization and reports. It does not replace those systems.**

### Proposed REST contract

The following is **product design, not existing functionality**. It preserves the GIVEN three-file workflow and human release before delivery. Use HTTPS, an OpenAPI contract and a versioned `/v1` namespace. The processing-time premise—roughly seconds to minutes for the example daily panel—is GIVEN, not a benchmark. A directly relevant precedent is Recast: its POST queues work and returns an ID; clients poll for completion. [Recast asynchronous-job documentation](https://docs.getrecast.com/docs/api-faq), as of research date.

| Concern | Concrete proposed behavior |
|---|---|
| **Authentication and keys** | For a private server-to-server integration, issue revocable high-entropy API keys per integration, tenant and environment; store key hashes, display secrets once, support rotation and scopes. Authorize each merchant within the agency tenant. Use bearer credentials in headers, never query strings. A caller-supplied merchant ID selects an already-authorized store; it cannot grant access. Browser/client apps need user login and delegated authorization rather than embedded server keys. |
| **Upload** | `POST /v1/upload-batches` creates private, tenant-bound slots for Meta spend, Google spend and Shopify orders. Return short-lived presigned upload URLs; the caller uploads CSV bytes directly to private storage. A completion step checks object presence, size, digest and validation state. For a small private pilot, authenticated multipart upload is a simpler alternative; neither route sends raw orders through an LLM prompt. Incremental documents a presigned first-party-data upload flow, an actual precedent rather than a made-up requirement. [Incremental upload docs](https://docs.incremental.com/docs/common-use-cases/file-upload/). |
| **Submit** | `POST /v1/audits` accepts owned upload handles, a matched date range, currency/timezone, margin with provenance, tier and review mode. Require an idempotency key tied to tenant and payload; retries return the same audit, not another charge. A changed payload with the same key is a conflict. Validate rights, schema, credit entitlement and completeness before accepting. Do not fetch arbitrary caller URLs. |
| **Asynchronous state** | Return HTTP `202 Accepted`, `audit_id` and a status URL after durable queue creation. `GET /v1/audits/{id}` distinguishes `validating`, `queued`, `running`, `awaiting_review`, `delivered`, `failed`, `cancelled`, and `expired`. A job can execute successfully yet conclude evidence is inconclusive; statistical outcome and job status are separate. Persist state across disconnects; include retry guidance and stable error codes. |
| **Polling / webhook / long request** | Polling is the initial supported route, with server-supplied backoff. Add optional signed webhooks for integrations that need them: pre-registered HTTPS targets, ownership checks, timestamp/signature verification, event IDs, bounded retry and duplicate handling. A webhook signals availability and contains IDs, not order rows. Holding a compute request open is possible but makes retries, client timeouts and human review fragile. Stream progress only as an optional convenience; it is not a durable result. |
| **Report delivery** | `GET /v1/audits/{id}/report` returns authorized, versioned JSON only after release; a separate download returns the matching PDF or a short-lived signed URL. JSON and PDF must derive from the same immutable report snapshot. Include model/schema versions, input fingerprint, dates, assumptions, warnings, intervals, MDE, evidence/review status and expiry. Repeated report fetches do not start or bill another audit. |
| **Quotas and rate limits** | Separate creation, upload-byte, concurrency and polling limits. **Proposed private-beta starting limits:** one running audit per merchant, five new submissions per tenant per minute, and sixty status/report reads per tenant per minute; also impose a prepaid audit budget and total pending-job limit. These are conservative author proposals, **not load-tested capacity or an industry norm**. Publish file/row/campaign caps after profiling. Return HTTP `429` with backoff, rather than charging surprise overages. Basis for limiting both objects and resources: [OWASP API risks](https://api-security.owasp.org/editions/2023/en/0x11-t10/). |
| **Versioning and reproducibility** | Version API input/output schemas separately from engine and classification policy. Store the exact engine version, preprocessing manifest and report hash with each job. Model revisions create a new report version; they never silently rewrite a delivered result. Announce breaking changes and a migration window agreed with consumers. Support cancellation and authenticated deletion independently of report availability. |

**CSV validation must be a shared server-side contract.** Reuse the current demo's intended validation rules, error language and missing-day behavior, but do not assume a clickable flow is executable backend validation. The Muse Space's implementation/source was not supplied, so exact rule parity is **UNVERIFIED**. The older repository upload UI is not that Muse demo. Local inspection shows a thin [schema checker](../ad_audit/ingestion/validators.py), [CSV schemas](../ad_audit/ingestion/schemas.py), and normalizers that can coerce malformed numbers to zero; these are reuse candidates requiring hardening, not a production validation contract. This is an internal implementation observation, not a public-market finding.

**Proposed validation acceptance checklist:** confirm required headers/types and file roles; reject malformed dates, nonfinite values and invalid spend; reconcile timezone, currency, export scope and requested range; preserve platform × campaign identity; detect duplicated exports and Shopify multi-line order rows; reconcile revenue/refund definitions and retain a validation manifest. Missing platform-reported conversion value means “comparison unavailable,” not zero attributed revenue. Reject silent range truncation, weekly/monthly aggregation or hidden campaign pooling. A declared absent platform needs explicit verified zero/absence handling, not an omitted file interpreted as zero. All changes affecting the engine's panel require the validation work in section 4.

**Missing-day rule:** an absent Shopify order row does not establish zero sales; a campaign omitted on a date does not automatically establish zero spend. Require documented complete export coverage and distinguish explicit zero from unknown. Missing interior **or boundary** days must block causal release until resolved; do not interpolate or zero-fill unknown outcomes. An order-level export alone may be unable to distinguish a true no-order day from an incomplete export: request corroboration or a separately validated daily aggregate input contract. The current Python [merge](../ad_audit/engine/aggregate_audit.py) and [campaign regression](../ad_audit/engine/campaign_regression.py) already warn/refuse campaign inference for detected missing Shopify days, while legacy totals can still be zero-filled. The service must not leak that fallback as a verified estimate. Freeze shared fixtures from the actual demo before implementation.

### Minimal MCP layer

The official `latest` specification resolved during this research to **revision 2026-07-28**. Its standard transports are **stdio** and **Streamable HTTP**; the latter carries messages through a single endpoint, returning JSON or request-scoped SSE. Implement the negotiated revision and compatibility behavior supported by target hosts; do not blindly copy an older connection-lifecycle tutorial. [Current specification](https://modelcontextprotocol.io/specification/2026-07-28), [transport definitions](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports).

**Proposed minimal tool set, using the same REST authorization/service layer:**

| Tool | Inputs and result | Boundary |
|---|---|---|
| `prepare_audit_upload` | Authorized merchant and file metadata → upload slots, accepted schema and expiry. | Only first-party private upload destinations. The client must actually support uploading files; a tool returning a URL does not supply that ability. Provide a secure browser upload fallback. |
| `submit_audit` | Validated upload handles, date/currency/timezone manifest, margin, tier, budget authorization and idempotency key → durable audit ID. | Consumes entitlement and creates a job; describe it as a write/cost-bearing operation. Human review remains required by default. |
| `get_audit_status` | Audit ID → job state, validation failures, review state and next-check guidance. | Read-only, tenant-authorized. No fake percentage or promised completion timestamp. |
| `get_audit_report` | Delivered audit ID → bounded structured report and authorized PDF access. | Read-only, aggregate output; cannot release an unreviewed job or retrieve raw orders. |

Cancellation and deletion can initially live in the authenticated account/REST control plane; do not hide them from users just because they are outside this minimal agent tool set. There is no `kill_campaign`, `set_budget` or ad-account write scope. Use input/output schemas and appropriate tool annotations, but enforce permissions, budgets and review server-side. MCP annotations describe behavior; the specification warns clients to treat them as untrusted unless supplied by a trusted server. [Tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).

**Long-running MCP work:** the current **Tasks extension** supports durable handles and polling, but requires explicit support from both server and client; it is not universal core behavior. Our ordinary tools should return the application audit ID immediately and allow status checks even without Tasks. If both sides support Tasks, map it to the same job rather than creating another queue or assuming the tool connection stays alive. [Tasks documentation](https://modelcontextprotocol.io/extensions/tasks/overview), as of research date.

**Hosted MCP means an operated, authenticated multitenant service.** For broad host compatibility, expose a stable HTTPS `/mcp` endpoint and OAuth user consent. The HTTP authorization spec is optional for MCP generally; for implementations supporting it, it specifies OAuth-based discovery and protected-resource metadata, audience-bound tokens, resource indicators and PKCE. Client ID Metadata Documents are recommended in the current revision; Dynamic Client Registration is optional legacy compatibility, not a universal requirement. Stdio normally takes credentials from the environment. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

Our proposed scopes are `uploads:create`, `audits:create` and `audits:read`, with explicit merchant grants and revocation. Verify issuer, signature, audience, expiry, scopes and tenant on every operation. Resolve tenant/store grants from trusted authorization records, never the model's assertions or a connection/session ID. Map agency users to their authorized merchants; key rotation and report URLs must not cross that boundary. Do not pass a ChatGPT/Claude access token through to Shopify/Meta/Google or reuse a token minted for another audience. The CSV-only design does not require those platform OAuth connectors. [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).

**Refund implications:** the GIVEN first-ten-orders, seven-day unconditional refund and full refunds for insufficient data, wrong numbers or lateness remain in force. A programmatic order is still an order; the initial-order counter must not reset with each API key or channel. Validate before capture where feasible; reserve credit once, capture/deduct once, and restore/refund on eligible failures. Distinguish a valid, honestly inconclusive report from insufficient data in the order terms, without narrowing the promised refund policy. Do not silently replace it with nonrefundable API credits. Whether a marketplace can implement this exact policy without extra manual handling is **UNVERIFIED**.

**Why per-audit usage pricing can be defended:** the billable unit is a reproducible, validated diagnostic with interpretation and review, not the matrix solve. The brief's “OLS compute is trivial” is a product premise; no hosting benchmark or penny-level cost estimate was measured. Pricing per result can align with buyer value and support cost even with low compute cost. Pricing per row, token, second or status request would instead expose a commodity-compute comparison and reward needless calls. The method alone is not demonstrated to be a moat; evidence quality, trusted handling and a useful decision process must earn the price. This is author commercial judgment, not a measured demand elasticity.

Start with direct per-audit entitlements for a committed buyer. Consider monthly prepaid audit bundles only after repeat frequency is observed, with the same per-merchant controls and clear refund handling. No volume discount, subscription minimum or cheap fully automated tariff is justified by current evidence. A low-price API that usually requires human explanation would likely worsen economics; the size of that effect remains UNVERIFIED.

## 4. Engineering scope

**Top finding: the OLS wrapper is the small part. A reviewable paid service is roughly 18–27 engineering person-days; adding production hosted MCP/OAuth brings the combined estimate to 25–38 person-days. These are planning estimates, not quotes.**

**Estimate assumptions, author judgment dated 2026-11-11:** one engineer familiar with this Python engine, reusable existing PDF generation, managed database/object storage/queue, CSV inputs only, a private beta with limited tenants, no promised uptime SLA, no Shopify/Meta/Google data connectors, and a minimal internal human-review control. Estimates include focused integration/security verification, not a statistical model redesign, enterprise certification, jurisdiction-specific legal work or time waiting for directory review. The scope is informed by the documented [async-report precedent](https://docs.getrecast.com/docs/api-faq), [upload pattern](https://docs.incremental.com/docs/common-use-cases/file-upload/), [OWASP risks](https://api-security.owasp.org/editions/2023/en/0x11-t10/) and [MCP authorization requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); the durations are **not supplied by those sources**.

## 6. Risks specific to machine-speed causal claims

**Top finding: confidence gating cannot detect all confounding. Preserve human review and separate statistical evidence, causal eligibility and business action. An HTTP success must never imply permission to cut spend.**

The GIVEN endogenous-spend failure is the critical counterexample: the engine can confidently estimate the wrong effect. Requiring a narrow interval or excluding zero does not fix that. HC3 addresses a form of variance estimation, not endogeneity or omitted carryover. A plausible-looking `positive` label is therefore not a causal certificate. Internal basis: [v2 calibration memo](../validation/v2-calibration-2026-11-09.md).

### Proposed release and consumer safeguards

| Risk | Proposed guardrail and machine-readable consequence |
|---|---|
| **Invalid/unidentified data** | Fail closed on unknown coverage, invalid values, incompatible dates/currency, singular design or unsupported preprocessing. `data_status=invalid` or `model_status=unavailable`; no causal point estimate, classification-driven action or legacy fallback disguised as inference. Distinguish schema rejection from a completed but inconclusive fit. |
| **A precise association presented as causation** | Separate `statistical_effect_label` from `causal_status`. Default causal status to `not_established` or `needs_review`; store an explicit assumption/eligibility record. Brand-demand feedback, carryover, promotions, omitted channels and serial-dependence concerns prevent causal release until an adequate design is established. A user checkbox alone is not proof of exogeneity. |
| **Missing uncertainty / false zero** | Require point estimate with signed interval, confidence level, standard error, MDE and its power definition, practical-equivalence bounds, usable date count, model/version and warnings. Return null/unavailable where unsupported. Do not replace a wide interval with zero, clamp negative effects away, or equate zero-in-CI with “non-incremental.” |
| **Profit decision confused with effect sign** | Keep the GIVEN four evidence labels separate from margin-based comparison. Include supplied/assumed margin and `break_even_iroas=1/margin`; the GIVEN assumed **40% → 2.50x** must remain explicit. Positive lift can be below break-even; practically-zero is not a general business-action code. With assumed margin or unestablished causality, emit no executable budget recommendation. |
| **Human gate removed by a fast API** | Default every new audit to `review_required`; computed jobs stop at `awaiting_review`, and a server-side reviewer releases the JSON/PDF snapshot. A caller cannot set `approved=true` or fetch around the gate. Expose actual review status and distinguish compute duration from the GIVEN **72-hour** reviewed delivery promise. Later automation is a separately validated product change, not a switch made safe by OAuth. |
| **Downstream system acts at volume** | Keep the tool surface diagnostic and read-only with respect to advertising. No spend-write credentials, budget changes or “KILL” enum in the automated action contract. Require downstream human approval for consequential action, cap jobs/credits/concurrency per tenant/merchant, flag repeat analyses and provide a global suspension mechanism. A third party can still misinterpret exported results; read-only access reduces direct impact but cannot enforce behavior outside our service. |
| **Repeated testing / cherry-picked windows** | Record dataset/window identity, related reruns and model version. Do not offer an agent unrestricted date-window search until it finds significance. Marginal intervals are not simultaneous guarantees across all campaigns and repeated looks. Apply a separately validated selection/multiplicity policy before alerting or automating decisions. |
| **LLM removes caveats or follows CSV instructions** | Treat campaign names, CSV cells and report text as untrusted data, never instructions. Bound and escape text; deterministic JSON and PDF must agree. Put evidence/review/causal status beside the estimates, not only in prose a model might omit. Test whether target clients preserve warnings. |
| **A bad result is discovered after delivery** | Track immutable versions and review provenance; support withdrawn/superseded status, visible warnings on later retrieval and a correction notification mechanism for subscribed consumers. Revoke downloadable objects where appropriate. Already downloaded copies cannot be recalled, so prevent initial release errors and explain that limitation. |

These controls are **author product design**, informed by the internal validation failures and the MCP tools specification's human-control guidance, not a claim that the current engine implements them. The tools specification recommends human ability to deny invocations; host confirmation is not a substitute for statistical review. [MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), as of research date.

**Concrete integration trap:** the existing [sample PDF generator](../scripts/gate1_pdf.py) derives `KILL`/`SCALE` wording from the interval's position relative to the margin threshold. A wrapper must not blindly serialize that wording or attach that PDF before causal-eligibility and review checks. Apply the release/wording policy to both formats. Carry forward the actual Gate 3 checklist into reviewer controls; its complete source was not supplied with this task, so exact checklist parity is UNVERIFIED.

**Do guardrails destroy the proposition?** They remove an unsafe promise of instant autonomous campaign killing. They preserve a narrower proposition: a reproducible, reviewed diagnostic delivered into an agency's stack, or a useful account of uncertainty and what experiment/data is needed next. If a buyer only values automatic decisive answers, this engine is a poor fit. If most accepted real jobs are inconclusive and buyers will not pay for a reviewed diagnostic, the API has no viable offer at these prices. The actual real-seller inconclusive rate, acceptance of that outcome, review burden and repeat purchase behavior are **UNVERIFIED**; synthetic calibration is not a commercial conversion forecast. Keep honest outputs and change/stop the offer if necessary, rather than weaken confidence rules.

### Order CSVs, PII and deletion

**The raw file is the sensitive boundary.** A standard order export can include contact information; local [Shopify schema code](../ad_audit/ingestion/schemas.py) currently even requires `Email`, although the campaign aggregate estimator does not need customer contact details. The API should offer a validated minimal upload schema that omits unnecessary identifiers, or strip them in an ingestion boundary before durable analytical storage. Names, email addresses, shipping details, URLs with identifiers and click IDs must not appear in logs or MCP results. Hashing an email does not by itself establish anonymity. Any changed ingestion contract needs the equivalence checks in section 4.

**Proposed handling:** TLS in transit; private encrypted objects with narrowly scoped upload/download access; authenticated object-level authorization; separate tenants and test/production data; redacted logs and traces; bounded file parsing; no raw-order echo in error messages; no training or secondary use of client data without a separate valid basis. Pass aggregate report fields to the host only with the merchant's consent and explain that host-side retention is a separate boundary. Recast explicitly warns that its MCP passes spend/performance data to the authorized LLM provider. [Recast MCP disclosure](https://docs.getrecast.com/docs/mcp-setup-guide).

Apply the GIVEN **raw-CSV deletion 30 days after delivery and report deletion 90 days after delivery** to all corresponding stored objects and derived data, not just visible filenames. Persist `delivered_at` when a released report becomes available, with scheduled expiry fields; re-fetching does not reset retention. Derived order-level staging should follow the raw-data deadline or be removed earlier. Index object versions, replicas, temporary files, queue artifacts and backups; test that restore cannot resurrect deleted client data. Retain only minimal non-payload billing/security records under a separately disclosed, justified policy.

The brief does not specify retention for abandoned uploads or failed/never-delivered jobs. **Proposed gap closure, not an existing policy:** expire unsubmitted uploads after **72 hours** and delete rejected/cancelled/terminal failed-job raw data promptly, with a proposed outer limit of **seven days after terminal state**; do not retain forever because `delivered_at` is null. These proposal values require policy adoption before launch. Expose authenticated early deletion, propagate it to derived data and invalidate report URLs. Client data already sent to a consumer's warehouse or AI host is outside our deletion API; disclose those copies explicitly.

Where UK GDPR applies, the ICO describes purpose-based retention, erasure and controller/processor contract obligations including documented instructions, security, subprocessors and deletion/return at termination. A contractual retention period does not override a valid earlier deletion obligation. These are conditional obligations, not an assertion that every merchant is covered by the same law; applicable jurisdictions, roles and transfer arrangements for this service remain **UNVERIFIED**. The ICO pages themselves say their guidance is under review following legislation. Sources as of research date: [storage limitation](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/storage-limitation/), [processor contract contents](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/accountability-and-governance/contracts-and-liabilities-between-controllers-and-processors-multi/what-needs-to-be-included-in-the-contract/).

### Always-on support changes the cost base

A manual service can receive files, inspect them and resolve ambiguity within the delivery promise. An endpoint must additionally handle expired keys/tokens, retries, queue outages, storage/deletion failures, malformed exports, version changes and consumer automation outside working hours. Log request/job IDs, authenticated tenant, versions, state transitions, redacted failure codes, review provenance and deletion execution; monitor queue age, error rates and stuck jobs without logging payloads or credentials. Add a visible service-status path, incident ownership, recovery runbook and honest response hours. Do not imply a continuous human-review or uptime SLA merely because an HTTPS endpoint exists. This operational assessment follows the proposed service surface and [OWASP's authorization/resource-consumption/API-management risks](https://api-security.owasp.org/editions/2023/en/0x11-t10/); no support-hours or outage-cost statistics are assumed.
